# Evidence before confidence

The difficult boundary is between lexical overlap, source support, and actual suitability. They are different. Fit reports policy-weighted source coverage. It does not establish whether an applicant really possesses a skill or deserves an interview.

CV input is synthetic Markdown with immutable bullet IDs. GitHub input is synthetic GitHub-shaped JSON. The reviewed MIT career-ops alias extractor is reused behind a typed adapter; local extensions add Linux/CMake and conservative negation/learning flags. A match cites exact UTF-16 offsets and a SHA256 of the UTF-8 source. Positive and negative mentions together produce a conflict, which receives no coverage credit. Repository language metadata is separately labeled and never adds CV credit. No model, secret provider or paid account is needed.

A small heading-based job parser separates required and preferred clauses from company boilerplate. An explicit `or` produces a one-unit alternative group. Other recognized skills each count as one unit. Required units weigh 1, preferred units 0.25. The weighted fraction is multiplied by min(1, CV years / required years). Preferred-only roles are capped at 25. These are visible product policies, not learned or calibrated probabilities. Whole-line negation and clause grouping can misinterpret complicated prose; the original source remains reviewable. Public extraction precision/recall is not measured.

Official Greenhouse public GET is bounded to a known hostname, validated board slug, 15-second deadline, 10MB response, and 12 selected engineering roles. Scripts/markup are treated as data and discarded. Raw job prose is processed in memory, replaced with a factual normalized skill/years summary and not retained. SHA256/time/bytes identify the actual response; a hash cannot reproduce deleted prose, so historical extraction cannot be re-run byte-for-byte from this repository. A new GET may yield different jobs. No arbitrary URL proxy, career-page scraper, application POST or account is provided.

Resume generation is deliberately a permutation, not a language-model task. Every source bullet remains byte-for-byte identical with its ID and exact span; the gate rejects edited text, shifted offsets, duplicate IDs, extra fields and stale source hashes. All output passes the server gate before a SQLite transaction creates a receipt. Markdown renders only validated known fields. This proves source integrity, not truth; a false input stays false. A source may change between deployments, so the submitted source hash must match the currently parsed CV. The UI has no private CV import or source editor.

The server binds loopback by default. A bearer edit token is required for writes; public binding refuses the default token. Reads expose synthetic data and recent synthetic receipts. This is not a multi-user service, privacy classifier, per-applicant permission system or application automation tool. JSON inputs are bounded to 32KB and safe error codes are returned without reflecting request text. Logs contain listening metadata; HTTP proof checks canary secrets stay absent. No raw CV logging is needed.

SQLite uses synchronous FULL with WAL; a committed receipt survives the tested graceful process restart. There is no distributed writer protocol, high availability, power-loss proof, backup service or tenant isolation. Docker Compose mounts a volume; Render free preparation uses ephemeral `/tmp` storage and must not be described as durable production hosting. No deployment was performed.

Evaluation freezes 72 agent-authored grades before scorer implementation. TF-IDF cosine over full postings is an interpretable keyword baseline; it deliberately has no requirement/negation model. The development comparison is not independent, held out, statistical validation or hiring evidence. Per-profile rankings and regressions remain visible. Acceptance is partial until an independent person provides relevance labels.

The original UI uses a narrow cobalt wordmark rail, an acid disclosure stripe, a ranked shortlist and an evidence ledger. It follows source-value scannability from the GOV.UK summary-list pattern, without copying assets. https://design-system.service.gov.uk/components/summary-list/ . It deliberately distinguishes semantic statuses through text as well as color and exposes actual provenance, gaps, score policy and evaluation limitations. Browser proof checks live interactions, errors and four widths; this is not a completed accessibility audit or usability study.
